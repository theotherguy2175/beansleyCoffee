# CLAUDE.md

Notes for whoever (human or AI) works on this repo next. This app was built
end-to-end in one long Claude Code session — this file captures the
non-obvious decisions and gotchas that came up, so they don't need
re-discovering.

## Architecture at a glance

- **Server** (`server/`): Express + TypeScript, ESM (`NodeNext` module
  resolution — relative imports need explicit `.js` extensions even in
  `.ts` source). Drizzle ORM over `better-sqlite3`, synchronous queries, no
  async DB driver overhead. Session auth via `express-session` backed by a
  sibling SQLite file (`sessions.db`), not JWT — chosen because this is a
  single-pod deployment (SQLite is single-writer anyway), and server-side
  sessions make "admin resets a password → invalidate that user's sessions"
  trivial instead of requiring a JWT denylist.
- **Client** (`client/`): Vite + React + TypeScript + shadcn/ui. shadcn
  components live in `client/src/components/ui/` as plain source files you
  own and edit directly (it's not an npm package) — they were largely
  **hand-written**, not generated by the `shadcn` CLI (see "shadcn CLI
  doesn't work reliably here" below).
- **Single container**: the server serves both the API and the built client
  static files (SPA fallback to `index.html` for non-`/api`, non-`/uploads`
  routes). One Docker image, one Kubernetes pod.

## Data model notes

- `coffees.coffee_type_id` is a **live FK** to `coffee_types` — it's a
  categorization used for filtering, so it's fine (and desired) for it to
  reflect the current type name if an admin renames a type.
- `coffee_strength_options` is a **per-coffee** list (e.g. Black Coffee →
  Regular/Decaf, Espresso → Single/Double shot), edited inline in the coffee
  form as a tag list, replaced wholesale on save (`replaceStrengthOptions`
  deletes and reinserts rather than diffing).
- `orders.syrup_names` stores a **JSON-encoded string array** (multi-select
  syrups), not a FK. `orders.size_oz` and `orders.strength_label` are plain
  denormalized values, not FKs either. None of the three need referential
  integrity — they're point-in-time snapshots of what the customer picked,
  validated against the *current* `syrups`/`sizes`/`coffee_strength_options`
  tables only at order-creation time (`order.service.ts`'s `createOrder`).
  If an admin later deletes a syrup, past orders still show what was
  ordered.
- `orders.coffee_name_snapshot` is the original example of this
  snapshot-not-FK pattern — copy it if you add more order-time fields.

## Auth / cookies — the thing that will bite you

Session cookies are `secure: true` in production, which means **browsers
refuse to send them back over plain HTTP**. This caused a real bug during
development: logging in appeared to work (the UI updates from the login
response body directly) but every subsequent request 401'd, because the
cookie was never actually stored.

- `app.set("trust proxy", 1)` + `cookie.secure` relies on either real TLS
  *or* an `X-Forwarded-Proto: https` header from a reverse proxy.
- Kubernetes (behind ingress-nginx + cert-manager) provides that header
  automatically → `COOKIE_SECURE=true` (the ConfigMap default).
- Plain `docker compose up` locally has **no reverse proxy in front** → must
  be `COOKIE_SECURE=false` (the docker-compose.yml default) or nothing will
  ever log in over `http://localhost:3000`.
- If you ever see "UI shows logged in, but every API call 401s," check this
  first before anything else.

Also: `COOKIE_SECURE` is parsed with `z.enum(["true","false"]).transform(...)`
in `server/src/env.ts`, **not** `z.coerce.boolean()` — Zod's `coerce.boolean()`
does `Boolean(value)`, and `Boolean("false")` is `true` (any non-empty
string is truthy). This bit us once already; don't reintroduce it for other
boolean env vars.

## Bootstrap admin is create-once, not sync-on-boot

`server/src/lib/bootstrapAdmin.ts` only acts if **no admin row exists yet**.
Changing `BOOTSTRAP_ADMIN_EMAIL` / `BOOTSTRAP_ADMIN_PASSWORD` and restarting
a container that already has an admin in its data volume does **nothing** —
this is expected, not a bug, but it's a common point of confusion ("I
changed the env var and my new admin login doesn't work"). To actually
rotate the bootstrap admin:

1. Log in with whatever admin credentials are currently live, and edit that
   user's email/password from Admin → Users (non-destructive, keeps all
   other data), **or**
2. Wipe the data volume (`.docker-data/` locally, or the PVC in k8s) for a
   truly fresh boot — destroys *everything* (coffees, orders, all users),
   not just the admin.

## Menu seeding

`server/src/lib/seedMenuIfEmpty()` runs after `bootstrapAdmin()` on every
boot, but only inserts anything if the `coffees` table is empty. It reads
`server/seed/coffees.json` and copies images from `server/seed/images/*`
into the uploads dir with fresh UUID filenames (same convention as the
multer upload middleware). Both the JSON and the images are **committed to
the repo and baked into the Docker image** (`Dockerfile` copies
`server/seed` into the runtime stage) — this is deliberate, so a fresh
deploy always has a working starter menu without a manual DB import step.
If you add coffees to the seed set, drop the image in `server/seed/images/`
and reference it by filename in `coffees.json`.

## Email

All outbound email goes through `server/src/services/emailTemplates.ts` —
a single branded HTML shell (table-based layout, inline styles — required
for email client compatibility, don't reach for flexbox/grid here) shared
by the maker notification, customer receipt, "your coffee is ready" email,
and the settings-page test email. SMTP credentials resolve **DB setting
first, env var fallback** (`getSmtpCredentials()` in `email.service.ts`) —
same pattern for `maker_notification_email`
(`getMakerNotificationEmail()`). This means an admin can fully configure
email from the Settings page even if the container booted with no SMTP env
vars at all (they're optional in `env.ts`).

The "ready" email only fires on an actual transition *into* `ready`
(`order.service.ts`'s `updateOrderStatus` compares against the previous
status) — don't remove that guard, or re-selecting "ready" from the
dropdown when it's already ready will resend the email.

## Things that were flaky in this sandbox (probably not your environment, but if déjà vu)

- **Default shell is `zsh`, not `bash`.** Bash-style array syntax like
  `${!array[@]}` fails with "bad substitution" in this repo's Bash tool.
  Use plain loops, `while read` over a heredoc/file, or shell out to
  Python/Node for anything array-heavy.
- **The `shadcn` CLI's `add` command silently "failed"** (reported success,
  wrote nothing) — turned out to be two things layered together: (1) very
  slow background writes that landed *minutes* later and clobbered
  hand-written stand-in files, and (2) **another concurrent Claude Code
  session was editing this same repo at the same time** (discovered via
  `ListAgents`). If you see files changing content you didn't write, or
  "changed on disk since last read" notices for files you just wrote,
  check for other active sessions on the same repo before assuming tooling
  is broken.
- **`docker-compose.yml` must never hold real secrets** — it's git-tracked
  (unlike `.env`, which is gitignored). Always use `${VAR:-default}`
  interpolation there and put real values only in `.env`.
- **`drizzle-kit generate` prompts interactively** (arrow-key select) when
  it detects an ambiguous rename (e.g. a renamed column), which isn't
  scriptable through a non-interactive shell. Workaround used here: since
  there was no real production data yet, we deleted `server/src/db/migrations/`
  and regenerated a single fresh consolidated baseline migration. Don't do
  this once the app has real deployed data — resolve the rename prompt
  properly (or hand-write the migration) instead.
- **Docker build stages need consistent native-module tooling.** `better-sqlite3`
  and `bcrypt` are native addons; every build stage that runs `npm ci`/`npm install`
  (client-build, server-build, *and* runtime) needs `python3 make g++`
  installed from the same base image — see the `base-deps` stage in the
  `Dockerfile`. Mixing glibc/musl bases between stages breaks the native
  binary.

## Browser-testing conventions used throughout

No automated test suite exists yet — verification was done by hand via the
`claude-in-chrome` MCP tools: boot the app with `docker compose up -d --build`,
click through the actual UI, check `read_network_requests` / server logs for
confirmation. A couple of things that made this more reliable:

- Prefer `read_page` → grab a `ref` → `computer` `left_click` with that
  `ref`, over clicking raw pixel coordinates. Coordinate clicks were
  noticeably flaky in this sandbox (missed elements, no-ops) in a way ref
  clicks weren't.
- Radix-based dropdowns (Select, DropdownMenu) sometimes didn't open with a
  synthetic `element.click()` via `javascript_tool` — use the `computer`
  tool's real click for those; `javascript_tool` clicks were reliable for
  plain buttons and form submission, though.

## Commands

```bash
npm run dev          # server (:4001) + client (:5173) concurrently
npm run build         # both workspaces
npm run typecheck      # both workspaces — run after every change, it's fast
npm run db:generate    # after editing server/src/db/schema.ts
docker compose up -d --build   # rebuild + redeploy the local test container
```

## Known gaps / possible follow-ups

- No automated tests (unit or e2e) — everything was verified manually.
- Client bundle is a single ~600KB chunk (Vite warns about this) — nobody's
  code-split it yet; probably fine at this app's scale but worth revisiting
  if it grows.
- `AlertDialogAction` (delete confirmations) doesn't show a loading spinner
  on click the way regular `Button` submissions do — lower priority, could
  be extended similarly to `components/ui/button.tsx`'s `loading` prop if
  it becomes annoying.
